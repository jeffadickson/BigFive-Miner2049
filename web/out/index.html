                Introduction

                Miner 2049er came out for the Atari 400 and 800 at the end of 1982 on a 16-kilobyte cartridge, twice the size of a standard Atari cartridge of the time. Bill Hogue of Big Five Software wrote it alone, entirely in 6502 machine language. This book reconstructs that cartridge by disassembling the ROM.

                The game itself is simple to describe. Bounty Bob, a Canadian Mountie, must walk over every section of every girder in an abandoned uranium mine while radioactive mutants patrol the levels. Picking up the prospecting tools left behind turns the mutants green, and for a short time he can eat them. There are ten "stations", each with its own gadget: slides, transporters, moving platforms, a lift, pulverizers and finally a cannon fired with TNT.

                What makes the program remarkable is how much it fits into 16K and how hard it pushes the hardware:

                • One ROM, two machines. The same 16K image boots on the Atari 400/800 and on the Atari 5200. At power-up it builds a table of pointers to the graphics and sound chips, which sit at different addresses on the two machines, and every later access goes through the table.
                • Ten colours on a scan line. The high-score screen runs a cycle-counted loop from RAM that rewrites all four playfield colour registers twice per scan line. It patches its own delay opcode to match the cycles the display chip takes, which change with the fine-scroll value.
                • Eight mutants, two sprites. Display-list interrupts cut the screen into four bands and reuse player 3 and the four missiles in each band. The collision registers are read band by band, so the game knows which mutant touched Bob.
                • The screen as the database. Which girder sections Bob has claimed is recorded nowhere except in the bitmap itself.
                • A game that runs in the interrupt. Almost all of the game runs in the vertical-blank interrupt. The main program only waits.

                None of the original source survives. Every name, comment and explanation here was worked out from the machine code. Where the evidence is indirect, the text says so.

                What is in this package

                • This book. History and background, the target hardware, the program's architecture, its algorithms with interactive figures, and the complete listing in an appendix.
                • miner2049er.asm, the commented source: about 9,250 lines for the ca65 assembler (part of the free cc65 suite). It assembles to an image that is byte-for-byte identical to the original cartridge. Every routine has a name and a header describing what it does, and every subroutine call is commented with what the called routine does.
                • cart.cfg, the linker configuration needed to rebuild the ROM.

                How the work was checked

                • Reassembly. The commented source is reassembled after every change and compared with the original ROM, which proves that no byte was misread.
                • Emulation. The cartridge was run in the Atari800 emulator (version 5.0, with its built-in AltirraOS firmware instead of Atari's ROMs), both as a 400/800 cartridge and as a 5200 cartridge. The emulator's monitor was used to stop at chosen instructions, read the beam position and step through code.
                • A 6502 harness. A small Python harness built on the py65 CPU emulator runs the ROM so that memory can be inspected, stations built on demand and single routines called.
                • Ported routines checked against the ROM. The claiming routine used in the interactive figure was compared with the ROM's own code at 1,322 random girder positions on all ten stations, with identical results.
                • Independent review. The text and the source comments were checked against the code by a separate reviewer, and the errors found were corrected.

                Every picture of the game in this book comes from one of three places: frames captured from the Atari800 emulator; movies rendered by the harness, which runs the cartridge's own code and draws each scan line from the display list, the player/missile memory and the GTIA registers, with the collision registers modelled so that the game's collision code works; or drawings made by this page directly from the cartridge bytes, which are embedded in it. Harness frames were compared with emulator frames of the same scenes. The letter shapes come from AltirraOS, so they differ slightly from a real Atari's.

                From a TRS-80 shop

                Radio Shack, Reseda

                Big Five Software began behind a Radio Shack counter. Bill Hogue first used a TRS-80 in high school, then worked at the Radio Shack store in Reseda, California, where he wrote BASIC programs between customers and moved on to assembly language. Jeff Konyu came into the store to buy parts; both were devoted Asteroids players. Hogue started a computer science degree at Cal State Northridge in 1979 and left in his second semester "when Big Five started up". The name came from a junior-high television class in which Hogue and four friends had called themselves "The Big Five".

                The company sold games by mail order from his parents' house in Van Nuys. Its first advertisement, for Super Nova, ran in 80 Microcomputing in July 1980. Over the next two years Big Five sold a run of arcade-style games for the TRS-80 Model I and III, among them Super Nova, Attack Force, Galaxy Invasion, Meteor Mission II, Cosmic Fighter, Robot Attack and Defense Command, plus Stellar Escort and Weerd by other programmers. It also sold the TRISSTICK, an adapter that let TRS-80 owners use Atari joysticks.

                The mail-order address in Super Nova's title screen in 1980, P.O. Box 9078-185, Van Nuys, is the same one printed in Miner 2049er's credits two years later.

                Super Nova and the Model I

                The TRS-80 Model I was a hard machine to write arcade games for. It had a Z80 processor at 1.77 MHz, a 64 x 16 character screen whose only graphics were 2 x 3 blocks inside each character cell (128 x 48 "pixels"), one colour, no sprites and no sound chip: the only route to a speaker was the cassette port.

                A disassembly of Super Nova (version 1.1, 1980), made before this one, shows how Hogue worked within that:

                • An off-screen frame buffer. Every frame is composed in RAM and then copied to the screen, to avoid flicker.
                • Pre-shifted sprite tables for the block-graphics cells.
                • Collisions by pixel overlap, tested in software.
                • Timing by instruction counting. The program uses no interrupts at all.
                • Self-modifying code everywhere. The PLOT routine, for example, stores SET 3,(HL) as a placeholder and patches the bit number into the opcode before running it. Six distinct patterns of self-modification appear in the program.
                • No sound. There is not one OUT instruction in Super Nova. Reviewers at the time noticed.

                The tools were Radio Shack's own: "Nothing fancy — I just used the standard Radio Shack editors and assemblers for Z-80 code."

                Moving to the Atari

                By 1982 the Model I had been out of production for a year and the TRS-80 games market was shrinking. Hogue wanted colour and sound. He considered the Color Computer and the Apple II and decided that "for the games I wanted to program, the Atari 400/800 was the best choice." The Atari gave him "color to play with" for the first time, though he had to learn a new processor and thought that "in many ways the Z-80 was the better CPU". He missed its block-copy instruction, LDIR.

                He did not develop on the Atari itself. In an interview with trs-80.org he said: "I wrote a cross-assembler running on a TRS-80 Model 16." Source was edited and assembled on Tandy's business machine, and the object code was sent to an Atari for testing over a serial port. So Miner 2049er was, quite literally, built in a TRS-80 shop.

                The game shipped in late 1982, the same month as Big Five's last TRS-80 release. In September 1983 Hogue told 80 Micro that the company had "officially left" the TRS-80 market, and that "if we hadn't come out with our Atari game at the time we did, we probably would have gone out of business." A black-and-white TRS-80 version of Miner, programmed by Kelly Bakst, was written but never released.

                Copies BC bytes from (HL) to (DE), incrementing both pointers, in one instruction. The 6502 has nothing like it. The usual replacement is a four-instruction loop: LDA src,X / STA dst,X / DEX / BNE loop, 4 + 5 + 2 + 3 = 14 cycles per byte and at most 256 bytes per loop. At the Atari's 1.79 MHz that is about 7.8 µs a byte, against 11.9 µs for LDIR on a 1.77 MHz Model I, so the 6502 version is faster. It costs more code, and it needs a second loop or a pointer in zero page for anything longer than 256 bytes. Miner's COPY and CLEAR routines are exactly this kind of loop (see CLEAR_MEM, which counts a negative length up to zero).

                The target hardware

                The Atari 400

                Atari announced its home computers in December 1978, showed the Atari 400 and 800 at the Winter Consumer Electronics Show in January 1979, and shipped them in November 1979. The 400 started life as "Candy", a low-cost design. Early in 1979 it became a full computer aimed at children and families, which is why it has a flat, spill-proof membrane keyboard instead of the 800's full-travel keys. Joe Decuir, one of its designers, later said the keyboard "didn't feel great, but it worked." Sources give its launch price as $495, $549.95 or $550.

                Strict FCC limits on radio interference shaped the design. Both machines are wrapped in cast-aluminium shielding, and rather than expansion slots they talk to their peripherals over a single serial bus (SIO). The 400 has one cartridge slot under a lid on top; the 800 has two. Cartridges, keyed connectors and a sealed case made the machine friendly to people who had never owned a computer.

                The 400 was planned with 4K of RAM (hence the name), shipped with 8K, and by 1981-82 was sold with 16K. Miner 2049er needs 16K of RAM. Prices fell steeply: about $400 with BASIC and a cassette recorder in 1981, $349 in 1982, and under $200 after rebates by the end of 1982. The 400 outsold the 800 by roughly two to one. About two million Atari 8-bit computers were sold between 1979 and 1985. Their main rivals were the Apple II, the TRS-80 and, from August 1982, the Commodore 64.

                The 400 and 800 share their electronics. Next to a MOS 6502 processor sit three custom chips designed under Jay Miner (who later designed the Amiga's chips): ANTIC, which fetches the display; CTIA or GTIA, which turns it into colour and adds sprites; and POKEY, which makes sound and reads the keyboard. A 6520 PIA reads the joysticks. The operating system lives in a 10K ROM at the top of memory.

                The 6502

                The 6502 is a small processor even by 1982 standards. It has one accumulator (A), two index registers (X and Y), all 8 bits wide, an 8-bit stack pointer whose stack is fixed at $0100-$01FF, a status register and a 16-bit program counter. There are no 16-bit registers and no multiply.

                What it has instead is zero page: the first 256 bytes of memory can be addressed with a one-byte address, which saves a byte and a cycle, and pairs of zero-page bytes can act as 16-bit pointers. A 6502 program treats zero page as its register file, and Miner uses all of it: $10-$6F hold the hardware pointer table and $70-$FF the game's variables.

                Reads a 16-bit address from zero page at zz and zz+1, adds Y, and stores A there. With Y = 0 it is simply "store A through the pointer at zz". Miner writes nearly every GTIA and POKEY register this way, for example STA (pCOLPF1),Y. Compared with STA $D017 it is one byte shorter and two cycles slower, and Y must be 0, which is why so many routines begin with LDY #$00.

                Time on a television

                An Atari draws an NTSC picture of 262 scan lines, 60 times a second. Everything in the machine is locked to that picture:

                • one scan line lasts 114 processor cycles of 1.79 MHz (63.7 µs);
                • one processor cycle is 2 colour clocks, the width of the narrowest coloured dot the hardware draws; a line is 228 colour clocks, of which a normal-width playfield shows 160;
                • one frame is 262 x 114 = 29,868 cycles.

                The processor does not get all of those cycles. ANTIC reads the screen from the same RAM over the same bus, and when it needs the bus it simply stops the 6502 for a cycle. This is called cycle stealing, and how much it steals depends on what is on the screen.

                Two consequences shape the program. A routine that must do something at a particular point on a line cannot know how long its instructions will take without knowing ANTIC's fetches on that line. And there is a lot more CPU time in the vertical blank, where ANTIC fetches almost nothing, than in the middle of the screen.

                ANTIC

                ANTIC (designed by Joe Decuir, Francois Michel and Steve Smith) is a processor in its own right. It follows a display list, a small program in RAM in which each instruction describes one horizontal band of the screen: its graphics mode, where its data comes from, whether it scrolls, and whether it should interrupt the 6502 when it is drawn. Once started it runs with no help from the CPU.

                Display list byteMeaning
                $708 blank lines
                $42 lo himode 2 text (40 columns), Load Memory Scan: take the data from address hi lo
                $0Eone line of mode E bitmap: 160 pixels, 4 colours
                $8Ethe same with bit 7 set: interrupt the CPU at the end of this line (a DLI)
                $41 lo hiJump and wait for Vertical Blank: start again at hi lo next frame

                Two kinds of interrupt come from ANTIC, both as NMIs (interrupts the CPU cannot mask):

                • The display-list interrupt (DLI) fires at the end of any display-list line with bit 7 set. Its handler can change colours or sprite positions for the lines below, which is how one set of hardware registers can serve several parts of the screen.
                • The vertical-blank interrupt (VBI) fires at scan line 248, after the last visible line. It is the natural place to run a game's frame.

                ANTIC also has registers the program uses directly: WSYNC ($D40A), which halts the CPU until the end of the current scan line when written; VCOUNT ($D40B), the current line divided by two; HSCROL ($D404), which shifts a line sideways by 0-15 colour clocks; DMACTL, PMBASE, CHBASE, CHACTL and the display-list pointer.

                The value written does not matter. The write makes ANTIC hold the 6502's RDY line low until the beam reaches the end of the current scan line, so the next instruction starts at a known horizontal position. It is the only way a 6502 program can line itself up with the beam. Miner's title kernel uses one WSYNC and then counts cycles for the next 12 lines without another.

                GTIA

                GTIA (George McLeod; machines built before late 1981 have the earlier CTIA) turns ANTIC's data into colour. A colour is one byte: the high four bits choose one of 16 hues and bits 1-3 one of 8 luminances, so $84 is hue 8 (blue) at luminance 4. Hue 0 is grey.

                GTIA also provides player/missile graphics, Atari's name for sprites: four 8-pixel players and four 2-pixel missiles, each a vertical strip the full height of the screen, with its own colour and horizontal position. Their shapes come from a block of RAM that ANTIC fetches line by line (PMBASE says where); to move a player up or down, the program moves its bytes within that strip. To move it sideways, it writes a new horizontal position. PRIOR sets which of players and playfield is in front and switches on two special modes Miner uses: multicolour players and the fifth player.

                GTIA keeps collision registers: one bit for every pair of sprite and playfield colour, or sprite and sprite, that has overlapped since the last write to HITCLR. Here is a detail Miner depends on. GTIA's read registers and write registers share addresses:

                POKEY and the PIA

                POKEY (Doug Neubauer) has four sound voices, each a frequency divider (AUDFn) and a control byte (AUDCn) with a 4-bit volume and a choice of pure tone or noise. It also scans the keyboard, reads eight paddle potentiometers, handles serial I/O and has a free-running 17-bit noise generator whose low byte can be read as RANDOM. Miner reads RANDOM through a pointer it calls pSKRES, because the write register at that address is SKRES.

                The 6520 PIA's port A ($D300) gives the two joystick directions as four bits each, 0 meaning pushed.

                Why the hardware mattered

                Each part of the game maps onto a hardware feature:

                • The mine is a bitmap in ANTIC mode E: 160 pixels across, four colours, two bits per pixel, 40 bytes per line.
                • Bounty Bob is three players laid over each other, which gives him four colours.
                • The mutants are player 3 and the missiles, reused down the screen by display-list interrupts.
                • The cannon is drawn with player 3 and the missiles, and the lift with player 3.
                • Collisions with mutants come from GTIA's collision registers; collisions with floors and walls come from reading the bitmap.
                • The sound effects use all four POKEY voices.

                Miner 2049er and Big Five

                Miner 2049er was Big Five's first Atari game, released at the end of 1982 (sources say November or December). Hogue built the game play first and added the mining theme and story afterwards. He combined Donkey Kong-style climbing with the Pac-Man ideas of covering the whole maze and of enemies that become vulnerable. The title is a pun on the "forty-niners" of the 1849 California Gold Rush, moved a century into the future. The folk song "Oh My Darling, Clementine" has the line "dwelt a miner, forty-niner", and the cartridge plays that tune after a game ends. Curtis Mikolyski designed levels for the series; Hogue coded them.

                The game was a hit. Creative Computing's reviewer called it "a greater game" than Donkey Kong in February 1983, and Tom Hudson of ANALOG wrote that it "looks as if it were designed, not just thrown together". It won Electronic Game of the Year at the 1984 Arkie Awards. Hogue said later that "Atari paid me a boatload of money for Miner." Licensing was handled by Barry Friedman's International Computer Group. Ports followed for about twenty systems, including the 5200, ColecoVision, Apple II, IBM PC, Commodore 64, VIC-20, TI-99/4A and a two-cartridge Atari 2600 version by Tigervision. It also inspired Matthew Smith's Manic Miner. Hogue's sequel, Bounty Bob Strikes Back!, followed in 1985 on a bank-switched cartridge, after which Big Five wound down.

                Reading the listing

                The listing follows a few conventions:

                • Names. Routines have upper-case names (for example CLAIM_FLOOR or GAME_VBI). Local labels inside a routine share a short prefix (CF_, MU_ ...). Zero-page variables have names such as BOB_X or SECTIONS. The hardware pointers are named after the register they reach, with a "p" in front: pAUDC3 is the zero-page word that holds the address of POKEY's AUDC3 register.
                • Headers. Each routine starts with a header that says what it does, what it takes and what it returns.
                • Comments. Inline comments explain the line or block they sit on. Lines whose comment begins with "if", "loop until" or "X = Y + Z" were summarised automatically from short instruction patterns; the rest were written by hand.
                • Data. Tables are shown in whichever form is clearest: sprites as bit pictures (# for a set bit, or 0-3 for two-bit pixels), text as screen codes with the decoded string, display lists one instruction per line.

                Positions use the game's own conventions:

                • Horizontal positions are in player/missile coordinates, where the playfield's left edge is 48 ($30). Bitmap routines subtract $30 to get the pixel column 0-159.
                • Vertical positions are bitmap lines 8-191, counted so that bitmap line y is drawn on scan line y + 32, which is also player/missile row y + 32. Bob's BOB_Y is the top of his sprite; his feet are 21 ($15) lines lower.

                One ROM, two machines

                The last six bytes of the cartridge serve both machines:

                $BFFA  .word RESTART      400/800: start address
$BFFC  .byte $00          400/800: "a cartridge is present"
$BFFD  .byte $FF          400/800: option byte;  5200: "skip the title screen"
$BFFE  .word COLD_START   400/800: init address;  5200: start address

                On the 400/800, bit 7 of the option byte marks a diagnostic cartridge. The OS jumps to the init address straight after reset, before it has initialised anything, so the game owns the machine from the first instruction. On the 5200, the BIOS reads $FF at $BFFD as "no title screen" and jumps through the word at $BFFE, which is the same address.

                COLD_START then works out which machine it is on. On the 5200, $F800 is the start of the BIOS character set, whose first two characters (space and "!") are made only of the bytes $00 and $18. On the 400/800, $F800 is in the middle of OS code. If all sixteen bytes from $F800 are $00 or $18, the game is on a 5200. It then builds the hardware pointer table described in the next chapter.

                The other differences are handled where they arise:

                • Input. On the 5200 the analog stick is read through POKEY's pot inputs and converted into the four direction bits of the 400/800's PIA joystick port (READ_STICK).
                • Keypad. POLL_KEYS translates the 5200's keypad codes into the 400/800 key codes the game expects. The # key becomes the space bar, PAUSE becomes ESC and RESET restarts the cartridge.
                • Fonts. The text renderer draws from whichever ROM font the machine has (FONTPAGE).
                • High scores. On the 400/800 they survive the RESET key, because the OS's warm-start flag tells the game it was not a power-up. On the 5200 there is no such flag, so COLD_START clears them at power-up; the keypad's RESET key goes straight to RESTART, so they survive that too.
                • Interrupt entry. The 400/800 OS saves A, X and Y before it calls the game's vertical-blank handler; the 5200 BIOS does not. So on the 5200 SET_VBI points the BIOS vector at a six-instruction stub, VBI_5200, which saves the registers itself and continues into the handler. Every handler can then end with the same NMI_EXIT on either machine.
                6502
                LDA abs,X (machine detection)
                load absolute, indexed by X
                bytesBD lo hi
                cycles4 (5 if the index crosses a page)
                flagsN, Z

                COLD_START's test is LDX #$0F / loop: LDA $F800,X / BEQ next / CMP #$18 / BNE not5200 / next: DEX / BPL loop. It reads sixteen bytes of whatever ROM is at $F800 and accepts only $00 and $18. BPL ("branch if plus") ends the loop when DEX takes X from 0 to $FF, whose bit 7 is set; counting down to -1 this way lets the loop include index 0 without a separate compare.

                Program flow

                The cartridge cycles through these screens:

                power-up / RESET
   COLD_START  ->  RESTART
                     credits (station 11, recorded demo)   --START-->  game
                     game-over tune (Clementine)
                     high-score screen   ---- 30 s --->  demo of station 1
                                         --START-->  game
game:  START_GAME -> PLAY_STATION:  prepare screen -> station -> next station / next player
       out of lives -> "Game Over" -> name entry -> high-score screen

                PLAY_STATION draws a station behind the "MINER 1 / PREPARE FOR / STATION 1 / ZONE 1" screen. The station is drawn pixel by pixel and takes a while, so the three-second prepare screen hides it. When the countdown ends, START_STATION switches the display to the game screen and installs two handlers:

                • GAME_VBI, the vertical-blank handler. It runs the whole game once per frame.
                • DLI_MUTANTS, the display-list interrupt. It runs four times per frame and manages the mutants.

                The main loop, GAME_LOOP, has almost nothing to do. It polls the console keys (OPTION, START, and digit keys during the demo), keeps the TNT readout up to date on station 10, and waits for one of two events: the turn ends (ALIVE reaches 0), or the end-of-station wipe finishes (WIPE_LINE reaches 0) and the next station is built.

                Running everything in the interrupt keeps the game's speed steady whatever the station looks like. There is no frame loop to fall behind.

                The vertical blank, step by step

                GAME_VBI does the following, in order:

                1. Read the keyboard (POLL_KEYS), count the frame, reload the display list pointer, and place the bonus box (the four missiles, double width, behind the bonus digits).
                2. Read the collision registers for the bottom band, set the status-line colours, and read the 5200 stick.
                3. If an item was just picked up, turn every living mutant edible.
                4. If the bonus is under 700, flash the bonus box, make Bob's face flicker and play a ticking sound that speeds up as time runs out.
                5. Handle pause.
                6. Make the current player's score blink (it is written with bit 7 set, and CHACTL bit 0 blanks such characters).
                7. Check whether Bob touched a deadly colour-1 object: the waste on station 6, the moving bar on station 8, a pulverizer on station 9.
                8. If Bob is dying, make him throb (the players change width) and play noise.
                9. Play the extra-life jingle.
                10. Move Bob (MOVE_BOB) and the moving platforms (UPDATE_LIFTS), set Bob's sprite position and size, claim girder sections under his feet (CLAIM_FLOOR), then move the pulverizers.
                11. Count down to the end of the turn after a death.
                12. On station 11 only: run the credits reveal and skip straight to step 16.
                13. Redraw the status line, update the items, run the bonus timer, and count the bonus into the score and wipe the screen once the station is clear.
                14. Add points for an eaten mutant.
                15. Check the phone-number cheat.
                16. In VBI_TAIL: advance the demo recording, run the cannon or the lift, and return.

                The hardware pointer table

                Building it

                Right after machine detection, COLD_START fills zero page from $10 to $6F with 48 pointers:

                $10 + 2r  ->  GTIA register r     ($D000 + r on the 400/800, $C000 + r on the 5200)
$50 + 2r  ->  POKEY register r    ($D200 + r,               $E800 + r)

                The code is two short loops. Y holds the chip's page ($D0 or $C0, then $D2 or $E8), A counts the register number up from 0, and X steps through zero page two bytes at a time:

                PWR_GTIA:  sta pHPOSP0,x      ; low byte  = register number
           sty pHPOSP0+1,x    ; high byte = the chip's page
           clc
           adc #$01
           inx
           inx
           cpx #$40
           bne PWR_GTIA

                Using it

                From then on the program almost never names a GTIA or POKEY address. It writes STA (pCOLPF1),Y with Y = 0 instead of STA $D017. ANTIC, at $D400 on both machines, is the only chip addressed directly. Counting through the listing:

                AccessCount
                (pointer),Y to GTIA or POKEY153
                (pointer,X) tricks47
                direct GTIA or POKEY addresses4 reads of CONSOL, all in code that runs only on the 400/800 (the 5200 has no console keys), plus the title kernel, which patches its own addresses

                The cost is time. STA (zp),Y takes 6 cycles where STA abs takes 4, and LDA (zp),Y takes 5 against 4. Y must be zero, so routines start with LDY #$00 and take care to keep it there. In return the table saves space: each indirect access is 2 bytes against 3 for an absolute one, about 200 bytes over the program, against 96 bytes of zero page and a few dozen bytes of set-up code. The real gain is that one binary serves two machines without a second copy of any routine.

                The (zp,X) tricks

                (zp,X) adds X to the zero-page address before reading the pointer. With the pointers two bytes apart, X = 2r selects pointer r. The table therefore doubles as an array of registers:

                DM_MISSILES:  sta (pHPOSM0,x)   ; X = 6, 4, 2, 0: HPOSM3, HPOSM2, HPOSM1, HPOSM0
              adc #$02
              dex
              dex
              bpl DM_MISSILES

                This loop places the four missiles side by side, 2 colour clocks apart, to form the fifth-player mutant. With absolute addressing the 400/800 version could have used STA $D004,X; the pointer table makes the same loop work on the 5200 too.

                Hogue went further and used whatever X happened to hold to reach a register from an unrelated pointer:

                CodeXPointer usedRegister reached
                lda (pAUDCTL,x)4$60 + 4 = $64RANDOM (the pSKRES entry)
                sta (pCOLPF1,x)8$3E + 8 = $46PRIOR
                sta (pAUDF3+1,x)1$59 + 1 = $5AAUDC3
                sta (pGRACTL-$3E,x)$3E$0C + $3E = $4AGRACTL

                These save a LDX or a LDY here and there, at the price of code that only works if X has the right value. Once, it does not: see "A harmless pointer bug" in the chapter on oddities.

                6502
                STA (zp,X)
                store indexed indirect
                bytes81 zz
                cycles6
                flagsnone

                Adds X to zz (wrapping within zero page), reads the 16-bit pointer from there, and stores A at that address. It is the 6502's least-used addressing mode, because few programs keep tables of pointers in zero page. Miner does, so for it this mode is an indexed register write. Note the wrap: with zz = $59 and X = 0 the pointer is read from $59/$5A, which straddles two entries of the table. That is exactly the bug in LAND_CHECK.

                Reading through a write name

                Because GTIA's read and write registers share addresses (see "GTIA"), a pointer named for a write register is also the way to read the register at the same address. READ_HITS, which saves the collisions of one screen band, reads them like this:

                READ_HITS:  ldy #$00
            lda (pSIZEP0),y    ; M0PL: missile 0 touched which players
            ora (pSIZEP1),y    ; M1PL
            ora (pSIZEP2),y    ; M2PL
            ora (pSIZEP3),y    ; M3PL
            sta MUT_SCORE,x
            lda (pGRAFP2),y    ; P3PL: player 3 touched which players
            sta HIT_P3-1,x
            rts

                The game writes SIZEP0-3 only to change sprite widths (Bob's throb when he dies, the lift's double width) and never writes GRAFP2 at all, because its players are drawn by DMA. A pointer is just an address; which register it reaches depends on whether the instruction reads or writes.

                The screen

                The display list

                BUILD_DLIST writes the game's display list at $2000:

                $2000  3 x "8 blank lines"

                Pixels

                In ANTIC mode E each byte holds four pixels, two bits each, leftmost pixel in the top bits. A pixel value of 0 is the background; 1, 2 and 3 select the colour registers COLPF0, COLPF1 and COLPF2. Miner uses them consistently:

                ValueRegisterUsed for
                0COLBKbackground (black)
                1COLPF0items, text, deadly objects (waste, crusher bar, pulverizers)
                2COLPF1ladders, slides, points numbers
                3COLPF2girders, platforms

                PLOT and its variants find the byte as LINE_LO/HI[y] + x/4, where the two 184-entry tables give the address of each bitmap line. They then use the pixel's position within the byte, x AND 3, to index two small tables:

                PIXEL_SET:   .byte $40,$10,$04,$01     ; +0  colour 1
             .byte $80,$20,$08,$02     ; +4  colour 2
PIXEL_MASK:  .byte $C0,$30,$0C,$03     ; +8  colour 3 (the mask is also colour 3)
             .byte $00,$00,$00,$00     ; +12 background
PIXEL_CLEAR: .byte $3F,$CF,$F3,$FC

                PIXEL_SET is indexed by PLOT_COLOR + (x AND 3), where PLOT_COLOR is 0, 4 or 8 for colours 1-3 and 12 for the background. The tables overlap: colour 3's entries are PIXEL_MASK itself, and the four zero bytes after it give the background. PLOT_IF_EMPTY draws only on background pixels, which is how ladders and slides avoid painting over girders.

                READ_PIXEL returns a pixel's colour and sets the Z flag if it is 3, which makes "is there a girder here?" a single subroutine call:

                sec
                sbc #$30
                tay
                and #$03         ; X = position in the byte
                tax
                tya
                lsr a            ; Y = byte in the line
                lsr a
                tay
                lda (PIX_PTR),y

                beq RP_DONE
                lsr a
                lsr a
                inx
                bne RP_SHIFT

                cmp #$03         ; Z = colour 3?

                6502
                CMP #imm
                compare with immediate

                cycles2

                Subtracts nn from A without storing the result, and sets the flags as if it had. Z is set when A equals nn; C is set when A is greater than or equal to nn (as an unsigned number). READ_PIXEL ends with AND #$03 / CMP #$03 so that its caller can write JSR READ_PIXEL / BNE not_girder and still have the colour in A for any other test. The listing's automatic comments turn CMP #n / BCC label into "if A < n goto label" for this reason: BCC (carry clear) after a compare means "less than", BCS means "greater or equal".

                Text in the bitmap

                The game uses two kinds of text. Fixed screens such as the title, prepare, name-entry and high-score screens use ANTIC character modes. Text inside the mine ("TNT Charge= 0 Tons", "DANGER", the credits, "Game Over") is drawn into the bitmap pixel by pixel by DRAW_CHAR. DRAW_CHAR reads the machine's ROM font, either at $E000 or at $F800 on the 5200, and can double the height. It paints 1 bits in the ink colour and clears 0 bits, so text erases whatever is behind it.

                Station colours

                The rules

                Each turn, START_STATION picks the three playfield colours at random. The background stays black. The code enforces two rules:

                • the three hues must all differ, and each must also differ from the hue that colour had on the previous turn;
                • the three luminances are 4, 6 and 8 in some order, so each colour has a different brightness.

                The second rule matters on a black-and-white television, which shows only luminance. With distinct luminances, items (colour 1), ladders (colour 2) and girders (colour 3) are still three different greys.

                The code

                START_STATION: ldx #$03
               stx CNT7
SS_CLEAR:      lda COLBK_V,x      ; keep only the hues of the old colours
               and #$F0
               sta COLBK_V,x
               dex
               bne SS_CLEAR
SS_HUE:        ldy #$00           ; random hue ...
               lda (pSKRES),y     ; RANDOM
               and #$F0
               sta MOVE_A
               ldx #$03
SS_HUE_CHK:    lda COLBK_V,x      ; ... not used by another colour
               and #$F0
               cmp MOVE_A
               beq SS_HUE
               dex
               bne SS_HUE_CHK
SS_LUM:        lda (pSKRES),y     ; random luminance 4, 6 or 8 ...
               and #$06
               beq SS_LUM
               clc
               adc #$02
               sta MOVE_B
               ldx #$03
SS_LUM_CHK:    lda COLBK_V,x      ; ... not used by another colour
               and #$0F
               cmp MOVE_B
               beq SS_LUM
               dex
               bne SS_LUM_CHK
               lda MOVE_A
               ora MOVE_B
               ldy CNT7
               sta a:$008A,y      ; COLBK_V + Y
               dec CNT7
               bne SS_HUE

                Three details are worth following through:

                • The old colours take part. SS_CLEAR strips the luminance from the three old colours but keeps their hues. The checks compare against all three slots, so the first new colour (slot 3) must differ in hue from all three old colours, the second from the two remaining old colours and the new first one, and so on. That is where the "differs from last turn" rule comes from; it is a side effect, not a separate test.
                • The luminance check never sees old values. SS_CLEAR left the old luminances at 0, which is never 4, 6 or 8, so only newly chosen luminances conflict. The result is always a permutation of 4, 6 and 8.
                • **AND #$06 / BEQ / ADC #$02** turns a random byte into 2, 4 or 6 (rejecting 0), then into 4, 6 or 8. Rejection sampling keeps the three values equally likely.
                6502
                STA abs,Y with a zero-page address
                store absolute, indexed by Y
                bytes99 8A 00
                cycles5
                flagsnone

                The colour variables live in zero page ($8A-$8D), but the 6502 has no "store zero page indexed by Y" mode: zero page,Y exists only for LDX and STX. So STA $008A,Y has to be assembled as a three-byte absolute instruction that happens to point into zero page. The listing writes it sta a:$008A,y, where a: forces ca65 to keep the absolute form so that the rebuilt ROM matches byte for byte. The same pattern appears in MU_HIT as lda a:$00E2,y.

                Girders and sections

                The unit of the game is the girder section, 4 pixels wide. DRAW_GIRDERS draws each section as three thin stripes of colour 3, two lines apart, and counts it into SECTIONS. On sloping girders each section is one line higher or lower than the one before. On flat girders, sections alternate between two stripe patterns, which gives them a brickwork look. That alternation turns out to be essential to how claiming works (see "Claiming the floor").

                Station machinery

                Station-specific set-up code adds the rest:

                • Stations 3 and 7: transporters. DRAW_TRANSPORTER draws the column of four booths from an 8-bit run-length pattern (BOOTH_SHAPE), each bit two pixels wide, and writes the digits 1-4 in them with the font renderer.
                • Station 6: the waste tank. DRAW_WASTE draws a solid colour-1 box and cuts "DANGER / Radioactive / Waste" into it in the background colour.
                • Station 8: the lift. The lift's platform, scissor arms and cart are drawn into player 3, and its track into the bitmap.
                • Station 9: the pulverizers. SETUP_PULVERIZERS draws the beam and posts and gives the four heads random starting delays.
                • Station 10: the cannon. The cannon goes into player 3 plus the missiles. The TNT store is drawn with its shelves and sign.

                Overlapping data

                The data area is full of sharing:

                • A list's 0 terminator is often the first byte of the next list.
                • Station 1's item list ends with the 0 that also serves as "no ladders, no slides, no platforms" for every station that lacks them.
                • Entry 0 of STATION_TABLE is also ITEM_SHAPES 33-36, the goblet and the three TNT bundles.
                • Station 10's eighth mutant record runs ten bytes into station 1's girder list. That is harmless, because the record's first byte, 0, means "no mutant".
                • Several girder lists start inside the slide list before them.
                • JUMP_ARC is 30 bytes long but is read for 32 entries; the last two come from the next table, BOB_SIZE, whose first two bytes are zero. They give Bob two more frames of hang time.

                Because the generated listing follows the ROM byte by byte, these overlaps show up as labels that sit in the middle of what looks like another table.

                Bounty Bob

                Three players, four colours

                Bob is drawn with players 0, 1 and 2 laid over each other at the same horizontal position: blue ($8A) for his coat, orange ($3A) for his face and hands, white ($0F) for his legs and the stripe down his front. START_STATION sets PRIOR to $31:

                PRIOR bitValueEffect
                01players 0-3 in front of the playfield
                4$10fifth player: the four missiles take COLPF3's colour (used by the mutants)
                5$20multicolour players: where players 0 and 1 overlap, GTIA ORs their colours

                Where players 0 and 1 overlap, $8A OR $3A = $BA, a green, so his hat comes out a fourth colour for free. Player 2 shows only where the other two are empty.

                Each animation frame stores the three layers back to back, 20, 17 and 17 lines, with each layer's first line shared with the previous layer's last: 52 bytes, stored 51 bytes apart, so a frame's last byte is also the next frame's first. DRAW_BOB copies them into player memory from the bottom up, and the blank lines at the ends erase his previous position as he moves.

                The movement state machine

                MOVE_BOB runs once per frame from GAME_VBI. It tests Bob's state variables in a fixed order and jumps to the routine for the first one that applies; that routine handles the frame and returns.

                OrderTestStateRoutine
                1SPECIAL = 1meltingMELT_BOB
                2SPECIAL = 2deadnone (GAME_VBI ends the turn)
                3SPECIAL = 3-7in the transporterTRANSPORT

                On a girder, the inputs are also tested in a fixed order. The button comes first, and only a fresh press counts: JUMP_LOCK is set to 6 while the button is held and must have run down to 0 before another jump. Then the stick: up, down, left, right, in that order, so a diagonal is read as its vertical part. Up and down start a climb only if there is a ladder; otherwise the stick falls through to walking.

                Walking moves Bob one pixel every other frame and cycles through three frames. After each step, the routine tests the bitmap under his feet with READ_PIXEL:

                • girder one line above his feet: the girder rises, so he steps up a line;
                • girder under his feet: nothing to do;
                • girder one line below: the girder falls, so he steps down a line;
                • no girder at all: he has walked off the edge and starts to fall.

                Bob follows sloping girders this way with no slope data at all: the bitmap is the collision map.

                Ladders. TRY_CLIMB_UP walks the ladder list and accepts a ladder whose foot (y + height) is level with Bob's feet or one line below them, and whose x is within two pixels of his. It then snaps him onto the ladder's x and starts the climb. MOVE_A and MOVE_B count the lines to the top and to the bottom; reaching either end puts him back on his feet. Frames 9 and 10 show him stepping on or off at the top.

                TCU_ENTRY:  iny                 ; bottom of the ladder = y + height
            iny
            clc

                6502
                SBC
                subtract with carry
                bytesE9 nn (immediate), E5 zz (zero page) ...
                cycles2 (immediate), 3 (zero page)

                Computes A - operand - (1 - C). There is no plain subtract on the 6502: you set the carry first with SEC (2 cycles) to mean "no borrow". After SBC, C is set if no borrow was needed, so SEC / SBC #n / CMP #2 / BCS is "if the unsigned difference is 2 or more". TRY_CLIMB_UP relies on the wrap-around: if the ladder's foot is above Bob's feet the difference is negative, which as an unsigned byte is 255 or so, and the same CMP #$02 / BCS rejects it. One unsigned compare covers both "too far below" and "above".

                The jump

                START_JUMP takes the direction from the stick (-1, 0 or +1), sets frame 11 or 12 depending on the way Bob faces, and clears MOVE_A, the position in the jump table. Then JUMPING runs every frame:

                • every other frame, it moves Bob MOVE_B pixels sideways, unless CHECK_LEFT or CHECK_RIGHT finds a wall;
                • every frame, it adds JUMP_ARC[MOVE_A] to BOB_Y. Past entry 31 it adds 1, so he keeps falling until he lands.

                The table goes up 11 lines, hangs for 2 frames, rises 3 more, hangs again, rises 2, hangs 3 frames at the top (16 lines up), then comes down slowly before the free fall takes over. The sound follows the arc: the pitch of voice 3 rises while Bob climbs (AUDF3 decreasing by 3 a frame) and falls as he comes down.

                From entry 21 on, each frame also calls LAND_CHECK, which counts FALL_LEN and looks for a girder under his feet. Forty frames of LAND_CHECK are fatal. Walking off a ledge, that is a fall of 40 lines. In a jump the count starts near the top of the arc, so landing 18 lines below the take-off point is safe and 19 lines kills him.

                6502
                ADC with a negative table
                add with carry
                bytes6D lo hi (absolute)
                cycles4
                flagsN, V, Z, C

                A + operand + C. JUMP_ARC stores its steps as signed bytes: $FF is -1, $01 is +1. Adding $FF to BOB_Y with the carry clear gives BOB_Y - 1 (plus a carry out that is ignored), so the same CLC / ADC table,X moves Bob up or down. Two's complement means the 6502 needs no separate signed add.

                Falling is one line down per frame with a falling whistle. When LAND_CHECK finds a girder, it also makes sure Bob's feet end up on the top stripe and not inside the girder, lifting him a line if needed.

                Slides. If Bob stands exactly at the top of a slide, he rides it: one line down and "step" pixels sideways per frame, using the jump frames 11 and 12, with a falling whistle (AUDF3 rising by one every other frame).

                Dying

                When a mutant, a hazard or the timer kills Bob, START_DEATH sets SPECIAL = 1 and two things run at once:

                • The throb. GAME_VBI counts DYING down 4, 3, 2, 1 every four frames and uses it to index BOB_SIZE and BOB_SIZE_X: the players switch between normal, double and quadruple width, with an x offset (0, -4, -8, -4) that keeps Bob centred.
                • The melt. MELT_BOB feeds a random byte in at his feet in each of the three players and shifts the column above it down one line. MOVE_B, the top of the shifted part, moves down a line each frame. When it reaches BOB_Y + $11, around his shins, he is a puddle of noise and SPECIAL becomes 2.

                Claiming the floor

                The idea

                CLAIM_FLOOR is the heart of the game. Bob must walk over every section of every girder, and the game must know which sections he has walked on. There is no table of sections anywhere in the program. The bitmap is the table.

                An unclaimed section is drawn as three thin stripes with gaps between them. Claiming it fills the gaps, so the section turns solid. Whether a section is claimed is therefore visible to the code the same way it is visible to the player: look at the pixels.

                Step by step

                CLAIM_FLOOR runs every frame while Bob walks or stands on a girder (not on the bottom floor, not while starting, dying, falling, sliding or in the transporter). FEET_OFFSETS gives the x of his two feet for the current animation frame, and CLAIM_AT runs once per foot:

                1. Is there girder under the foot? READ_PIXEL at the feet line must return colour 3. If not, nothing happens.
                2. Is it unclaimed, and which pattern? It reads the next line down. If that line is background, the gaps are at +1, +3 and +5 (three gap rows). If it is girder, it reads the line after: background means gaps at +2 and +4 (two gap rows); girder means both lines are solid, the section is already claimed, and nothing happens.
                3. Score it. SECTIONS goes down by one and ADD_SCORE adds 5.
                4. Find the section's left edge. Along the first gap row it looks at the pixel left of the foot. If that is girder, the foot was on the section's first pixel. Otherwise it steps left up to 3 more pixels looking for girder. If it finds none, the section must start further right: it steps 4 right and scans right until it finds girder, then backs up 5. Either way, the first gap pixel is one to the right of where it stopped.
                5. Fill. It plots 4 pixels of colour 3 in each gap row, two lines apart.

                The left-edge search works because neighbouring sections never have their gaps on the same lines. On a slope, the next section is a line higher or lower. On a flat girder, sections alternate between the two stripe patterns, the brickwork. In a gap row, a neighbour shows up as girder.

                What it saves

                The design costs nothing in memory: no flags, no counters per section, nothing to initialise when a station is drawn beyond the single SECTIONS count. It also makes the drawing and the game logic impossible to get out of step, since there is only one copy of the truth. The price is time, since every check is a call to READ_PIXEL, which computes a line address and shifts bits, but Bob only moves a pixel every other frame.

                There is one sharp edge. If the code were ever asked to claim at a spot where the gap row has no girder pixel anywhere to its right, the rightward scan would never end: the X position wraps around and the line is read again forever. Bob's feet cannot reach such a spot in play, so this never happens; it turned up only when the harness put Bob's feet at random places, including the middle of a girder's stripe.

                6502
                LSR A
                logical shift right, accumulator
                bytes4A
                cycles2
                flagsN (always 0), Z, C (gets bit 0)

                Shifts A one bit right; bit 0 goes into the carry. Two LSRs divide by 4, which turns a pixel column into the byte within the line (four pixels per byte). READ_PIXEL also uses LSR pairs to move a pixel's two bits down to the bottom. MOVE_BOB uses LSR the other way round: it shifts the joystick byte right one bit at a time and tests the carry with BCC/BCS, reading the four direction bits in turn without any masks.

                Mutants

                The problem

                A station has up to eight mutants. The hardware has four players and four missiles, and Bob has already taken three players. What is left is player 3 and the missiles: two sprites for eight monsters.

                The answer is that a sprite's horizontal position, width and colour are registers, read by GTIA afresh on every scan line, while its shape is a full-height strip of memory. Put eight shapes at eight different heights in the strip, and change the horizontal position between them, and one sprite becomes several.

                Four bands

                The game's display list has four DLIs: at the end of the status line, and after bitmap lines 46, 93 and 140. They divide the mine into four bands of about 47 lines, and the stations are designed so that each band contains at most two mutants and no mutant crosses a band boundary.

                In each band:

                • player 3 draws one mutant, with its colour in COLPM3;
                • the four missiles draw the other. Each missile is 2 pixels wide. DLI_MUTANTS places them side by side, 2 colour clocks apart, and PRIOR's fifth-player bit gives all four the colour COLPF3. Together they make one 8-pixel sprite.

                What each DLI does

                3. Band effects.                 4. Move and animate two mutants. The rest of the handler is the mutants' game logic: patrol steps, turning round, the shimmer, the edible countdown, being eaten. Two of the eight records are updated per DLI, so all eight are updated once per frame.

                The collisions for the bottom band are saved at the start of GAME_VBI, which is the next thing to run after the bottom band is drawn.

                Timing

                Running in the 6502 harness, DLI_MUTANTS took between 256 and 1,290 cycles per call across five stations (about 260 to 640 on average, depending on the band), and GAME_VBI from about 3,030 cycles on station 1 to as many as 5,800 on station 5. A band of mode E lines leaves the CPU roughly 60 of each line's 114 cycles, so even the longest DLI uses only about 22 of its band's 47 lines. That leaves the main loop plenty of time. The order inside the handler matters more: the DLI fires at the end of the boundary line, and the sprite positions must be written before the beam reaches the band's first mutant a few lines further down. So the collision save and the positioning come first, and the slow mutant logic last, while the band is already being drawn.

                A mutant's shape is never redrawn because of the multiplexing. Each mutant has its own rows in the player or missile strip, so its shape is only rewritten when it animates or moves vertically. The sharing costs only register writes.

                6502
                PHA / TXA / PHA / TYA / PHA
                save registers on the stack
                bytes48 8A 48 98 48
                cycles3 + 2 + 3 + 2 + 3 = 13

                An NMI saves only the program counter and the status register. A handler that uses A, X and Y must save them itself, and the 6502 can push only A, so X and Y go through A. NMI_EXIT, the common tail of every handler in the game, does the reverse (PLA / TAY / PLA / TAX / PLA / RTI). On the 400/800 the OS has already saved the registers before calling the VBI, but not before a DLI; on the 5200 the BIOS saves nothing. Miner's DLIs save their own, and its 5200 VBI stub saves them too, so all handlers can end the same way.

                Behaviour

                Each mutant patrols back and forth along a girder. Its station record gives:

                • its height and starting position;
                • the length of its patrol and its speed (frames per step);
                • the timing of its shimmer (its brightness pulses up and down by 2).

                The step delay is the record's value + 1 - zone, at least 1, so mutants get faster as the game goes on.

                When Bob picks up an item, ITEM_GOT is set, and on the next frame GAME_VBI turns every living mutant edible. Each turns green ($C6) with an edible counter of $AF - 16 x min(zone, 9): 159 in zone 1, falling to 31 from zone 9 (the subtraction runs with the carry clear, so it is one less than $B0 - 16n). It stays green for that many frames, then blinks: purple for 5 frames, green again for half the previous time, and so on until the counter reaches zero. The blinking speeds up as a warning. In zone 1 a mutant stays edible for about six seconds; from zone 9 on, about one and a half.

                Touching an edible mutant eats it for 80 or 90 points, chosen at random, and the mutant shows the number, flashing in random colours, while a rising tone plays for about two seconds. Touching a mutant that is not edible kills Bob.

                6502
                SBC without SEC
                the edible-time off-by-one
                bytesE5 zz
                cycles3
                flagsN, V, Z, C

                GV_EDIBLE_TIME computes $B0 - 16 x min(zone, 9) with LDA #$B0 / SBC ITEM_GOT, but the compare and the four ASLs before it leave the carry clear, and nothing sets it. On the 6502 a clear carry means "borrow one", so the result is one less than intended: 159 frames instead of 160 in zone 1. Nobody could ever see the difference, but it is the kind of slip that only shows up in a disassembly.

                Items, scoring and time

                Items

                Items are small pictures stored as whole bytes (four pixels per byte) and copied straight into the bitmap. Each has a width, a height and a points value. When Bob touches one, UPDATE_ITEMS does five things:

                • draws the points number over the item ("100" ... "500"; the points byte doubles as the shape number of the number picture);
                • erases the rest of the item;
                • adds points x 100 to the score;
                • sets ITEM_GOT, which turns the mutants edible;
                • plays a falling whistle.

                The "BF" (Big Five) logo on station 7 is worth 1,100. On station 10 the items are bundles of TNT; their points value, 1 to 3, is also the number of tons added to the cannon's charge.

                On station 5 one item is a trap. UPDATE_ITEMS treats the goblet (shape 33) specially there: touching it sets KILLED. The goblet sits just above Bob's starting place, so a jump straight up at the start of the station kills him. This was confirmed in the emulator.

                Score

                The score is six decimal digits, one per byte. ADD_SCORE adds a value to any digit and carries upwards. Points come from:

                EventPoints
                claiming a section5
                item100-500 (BF logo 1,100)
                eating a mutant80 or 90
                bonus left at the end of a stationcounted in at 100 a tick

                When the score first reaches 10,000, Bob gets an extra life. The award is detected by the ten-thousands digit becoming non-zero while XLIFE still holds its initial value. A jingle then plays: in each 16 frames, 8 frames of one note on a blue background and 8 of a higher note on black.

                The bonus timer

                Each station starts with a bonus of BONUS_BASE + 500 per zone (at most 9,900), shown in a box on the status line. The box is the four missiles, set to double width. The bonus drops by 100 every three seconds. Below 700 the box flashes, Bob's face flickers and a tick plays faster and faster. If the bonus reaches zero before the station is clear, Bob dies.

                The end of a station

                When the last section is claimed:

                1. Bob vanishes.
                2. TALLY counts the bonus into the score 100 at a time, with a click each time.
                3. WIPE removes the screen from the bottom up. Each frame it overwrites the next display-list line with a JVB (jump and wait for vertical blank), so ANTIC simply stops drawing there, and a rising tone plays.
                4. When the wipe reaches the top, the main loop builds the next station.

                Station machinery in detail

                Transporters (stations 3 and 7)

                To use a transporter, Bob stands still inside a booth and presses a digit key 1-4. The transporter runs as a five-state sequence in TRANSPORT:

                1. Bob dissolves into sparkles: SPARKLE_BOB ANDs every line of his sprite with a random byte. A random buzz on voice 3 grows louder.
                2. A short pause follows.
                3. Bob appears at the destination booth, while sparkles linger at the old booth and his colours flash in both booths.
                4. He sparkles in place at the new booth.
                5. He re-forms as the buzz fades.

                Afterwards the transporter is locked for five steps of 64 frames, about five seconds (128 frames each from zone 5 on, about ten seconds), and the booths are red until it recharges. They are also red, briefly, when the station starts.

                The lift (station 8)

                Standing on the lift and pressing the space bar (the # key on a 5200) hands the joystick to the lift. The stick then drives it left and right along its track and up and down. It rises at half the speed it falls: a line every 4 frames up, every 2 frames down. Bob rides along, and pressing space or the button again gives control back.

                The lift is player 3 in the band that contains it. As it moves up or down, LIFT_CONTROL rewrites the top of its column of player data: it clears the line above, writes the two-line platform and one more line of the scissor pattern. The arms seem to extend and fold because the pattern's phase steps through a seven-line cycle.

                Pulverizers (station 9)

                Four heads hang from a beam. Each waits, drops 22 lines, rises again and waits for a delay that shrinks with the zone. Each head's top line is a thin rod. As the head descends, that line is left behind each frame, so the rod grows down from the beam with no extra drawing code. The heads are drawn in colour 1, and touching colour 1 on this station is fatal. Station 9's moving platforms behave as lifts: the code holds each one at the end of its run until Bob stands on it.

                The cannon (station 10)

                Bob collects TNT bundles worth 1-3 tons each, then steps into the cannon's mouth. The cannon then follows him along its track, and the button fires it:

                ChargeResult
                1 tonBob reaches the first platform
                2 tonsthe second platform
                3 tonsthe third platform
                4 tons or morehe is shot off the top of the screen and falls back upside down

                With 4 tons or more loaded, the word "DANGER" appears on the screen as a warning. After such an over-charged shot, DRAW_BOB_FLIPPED draws Bob upside down for the rest of the turn, by copying his sprite top-to-bottom instead of bottom-to-top. SHOW_TNT keeps "TNT Charge= nn Tons" up to date on the screen.

                The title-screen kernel

                Ten colours on a line

                The high-score screen surrounds the table with a frame of 36 "5" characters whose colours march round it like theatre lights. Along the top and bottom there are ten lights on one line of ANTIC mode 7 text. Mode 7 can colour a character with one of four registers, COLPF0-3, chosen by the top two bits of its code. Four registers, ten lights.

                The ten lights are made like this:

                • the left four are playfield characters using COLPF0-3;
                • the middle two are players 1 and 2, with their own colour registers, holding copies of the "5" glyph;
                • the right four are playfield characters using COLPF0-3 again, after the colour registers have been rewritten while the beam is in the middle of the line.

                So on each of the row's 12 visible scan lines, the four playfield colour registers must hold the left lights' colours while the beam crosses the left third of the screen, and the right lights' colours by the time it reaches the right third. The program that does this is TITLE_KERNEL.

                The kernel

                TITLE_KERNEL is 62 bytes, copied at start-up from the cartridge at $9630 to RAM at $0400. Assembled for $0400 it reads:

                Everything in it that changes is patched by the cartridge code:

                • Colours. Every frame, KERNEL_COLS_TOP and KERNEL_COLS_BOTTOM write the eight LDA # operands from a ten-colour ring, CHASE_COLOURS, starting at the current rotation.
                • Chip addresses. KERNEL_COLS_TOP also rewrites the high byte of each STA COLPFn with the GTIA page taken from the pointer table, $D0 or $C0. The kernel cannot afford the pointer table's indirect stores, so it uses absolute ones and fixes their addresses for the machine it finds itself on. That is the reason it runs from RAM: a ROM cannot be patched.
                • Delays. SET_FINE_SCROLL writes the opcode of both delay instructions.

                There is one WSYNC at the start and none inside the loop. From the first line to the twelfth, the kernel keeps step with the beam only by taking exactly as long as a scan line.

                6502
                ORA (zp,X) as a delay
                OR indirect, used for its timing

                cycles6

                The kernel needs 18 cycles of padding after its last colour write. A NOP is 1 byte and 2 cycles, so 18 cycles of NOPs would be 9 bytes; three ORA ($B1,X) do it in 6 bytes. Any 2-byte, 6-cycle instruction would do, provided it has no side effects that matter: this one only changes A, which is reloaded at the top of the loop, and reads from wherever the pointer at $B1+X leads, which is harmless on this screen.

                Counting the cycles

                One pass of the loop takes:

                PartCycles
                8 x (LDA # / STA abs)8 x 6 = 48

                delayd = 3, 4 or 5
                DEX / BEQ (not taken) / JMP2 + 2 + 3 = 7

                A scan line is 114 cycles, but ANTIC takes some of them. On each line of this mode 7 row it fetches one byte of character data per character (24 of them, because a horizontally scrolled line fetches the wider amount), refreshes the dynamic RAM (9 cycles) and fetches player/missile data (5 cycles). That leaves about 76 cycles for the CPU, which matches the loop with d = 3. Why then change d?

                The answer came from stepping through the kernel in the emulator and reading the beam's horizontal position at the top of every pass:

                HSCROLDelay opcodeLoop lengthBeam position at the top of each pass (cycle)Cycles ANTIC took per line
                0CPX zp (3)76110, 110, 110 ...38
                2CMP zp,X (4)77110, 110, 110 ...37

                At every scroll value the pass starts at the same beam position on every line, so the loop is exactly one line long, and the cycles ANTIC takes from a line change with the fine scroll: 38 at HSCROL 0, 37 at 2-8, 36 at 10-14. In the emulator's cycle-by-cycle model of ANTIC, shifting the character fetches sideways changes how many of the nine refresh cycles still fit on the line. SET_FINE_SCROLL picks the delay that makes the loop exactly as long as what ANTIC leaves:

                SET_FINE_SCROLL: sta HSCROL
                 ldx #$E4            ; CPX zp, 3 cycles   (HSCROL 0-1)
                 lsr a
                 beq SFS_PATCH
                 ldx #$D5            ; CMP zp,X, 4 cycles (HSCROL 2-9)
                 cmp #$05
                 bcc SFS_PATCH
                 ldx #$06            ; ASL zp, 5 cycles   (HSCROL 10-15)
SFS_PATCH:       stx KERNEL_DELAY2
                 stx KERNEL_DELAY1
                 rts

                The title code scrolls two colour clocks at a time, so only the even values 0-14 ever occur. For each of them, the delay the code chooses is the one that the emulator's cycle-by-cycle model of ANTIC says is needed. Hogue would have found these thresholds on real hardware, by trial or by working through ANTIC's fetch timing; nothing in the code says which.

                A loop one cycle too long would drift two colour clocks per line, 24 colour clocks over the 12 lines, and the colour changes would cut diagonally through the lights. A check of 150 captured frames, covering six of the eight scroll phases, found every light a single colour from top to bottom.

                6502
                CPX zp / CMP zp,X / ASL zp
                three delays of different lengths
                bytesE4 B1 / D5 B1 / 06 B1
                cycles3 / 4 / 5
                flagsCPX and CMP set N, Z, C; ASL changes $B1 and sets N, Z, C

                All three are two bytes long, so any of them can be patched into the same slot without moving the code after it. Their cycle counts differ by one each, which is the step the kernel needs. CPX and CMP only read; ASL writes its result back to $B1, which is the first byte of the title's temporary storage and is not used while the kernel runs. The kernel patches only the opcode byte; the operand $B1 stays.

                The rest of the screen

                • The rows never move. The top and bottom rows are single lines of mode 7 text kept in ROM. HSCROL slides each row by 0-14 colour clocks, two at a time every five frames (the title loop counts four frames, then the new phase is shown on the next one), which is up to two character cells. Each time the scroll wraps, the colours rotate one light, so the eye sees continuous motion.
                • Side columns. Players 0 and 3, in double-line resolution, form the side columns. A display-list interrupt on every text line recolours them. They move by redrawing into a second player/missile buffer and switching PMBASE between $0400 and $1C00, which is double buffering.
                • Smaller effects. The ten score lines get a moving rainbow from the same interrupts, "HIGH SCORES:" pulses in brightness, "START" blinks in inverse video, and a soft tone repeats.

                The display list itself is in ROM ($8000). Its final JVB instruction's address bytes are also the first two characters of the bottom row of lights, so the jump target is nonsense. That is harmless, because TITLE_VBI reloads the display list pointer every frame.

                The credits and the demo

                The credits

                After power-up the game plays station 11, a station of plain girders with no mutants, which hides the credits. The credits are drawn at the start in pixel colour 1, whose register is set to black, so they are invisible. Bob, driven by the recording DEMO_CREDITS, walks the girders. Every frame GAME_VBI looks at a one-pixel column 30 lines tall through him, starting 12 lines above his head, and repaints every colour-1 pixel there in colour 2, so the words appear behind him as he passes. When he reaches the bottom right, colour 1 is made visible, the full text appears, and a display-list interrupt (DLI_RAINBOW) runs alone, with no vertical-blank interrupt, striping the text with a scrolling rainbow while Clementine plays.

                The demo recorder

                Both Bob in the credits and Bob in the station-1 demo are played from recordings in the ROM. A recording is a list of (input, frames) pairs:

                BitMeaning (0 = active)

                2stick left

                RecordingPairsFramesLength

                Playback costs almost nothing. DEMO_PTR points at the current pair; its high byte doubles as the flag "a recording is playing", because no recording lives in page 0. The rest of the game cannot tell a recording from a player: Bob's movement, the mutants, the collisions and the claiming all run exactly as in a real game. The game is deterministic apart from POKEY's RANDOM, which on station 1 affects only the colours and the points for an eaten mutant, so the same recording always produces the same walk.

                The run lengths have the irregular values (81, 11, 6, 9, 29 ...) of a hand on a joystick rather than a hand-written script, which suggests the recordings were captured from real play. Nothing in the cartridge records; the capture routine, if there was one, stayed on the development system.

                Other screens

                The phone-number cheat

                During a game, typing Big Five's telephone number, 213-782-6861, then SHIFT plus a digit, warps to that station (0 means station 10). PHONE_CODE compares each digit typed with the bytes of the number as printed at the end of the credits text, "(213) 782-6861", skipping the bracket, the space and the dash. The printed text and the cheat code are the same bytes. A wrong digit starts the count again, and a held key repeating the same digit is ignored. On the 5200, the lower fire button plays the part of SHIFT.

                Sound and music

                POKEY's four voices are used for different effects:

                VoiceUsed for
                1game-over tune melody, siren on the prepare screen, death noise, time-running-out tick, title tone
                2game-over tune harmony, mutant being eaten, name-entry clicks

                GAME_OVER_TUNE plays "Oh My Darling, Clementine" three times: on voice 1, then on voice 2, then on both together. The tune table holds the melody as POKEY dividers ($28 C, $35 the G below, $1F E, $1A G, $1D F, $23 D, $2A B) with lengths in frames. Voice 2 does not read the table; its note is calculated from the melody note as (note - $1D) x 4 + $79, which places it roughly two octaves lower, and a single special case covers note $1A. Each note starts at full volume with a pure tone and decays one step per frame, which sounds like a plucked instrument. START, the button or a digit key cuts the tune short.

                Tricks lost to time

                Many of the techniques in this program were common knowledge among Atari programmers in 1982 and are now mostly forgotten:

                • A pointer table instead of fixed addresses lets one binary drive chips at different addresses on two machines.
                • A diagnostic cartridge owns the machine from the first instruction.
                • Self-modifying code for timing: delay opcodes chosen for their cycle counts and patched into a scan-line loop to match what ANTIC leaves at each fine-scroll value.
                • Self-modifying code for portability: the high bytes of absolute stores patched with the chip's page at run time.
                • Mid-line colour changes go beyond the hardware's colours-per-line limit.
                • Sprite multiplexing with display-list interrupts, and collision registers read per band.
                • Fifth-player mode, which turns the four missiles into one more sprite.
                • Double-buffered player graphics by flipping PMBASE.
                • The screen as the database: the girders' claimed or unclaimed state lives only in the bitmap.
                • Input recordings played through the input routines, so the demo and the credits are the real game.
                • A display list rewritten on the fly to wipe the screen line by line.
                • Hidden text revealed by recolouring pixels whose colour register is set to black.
                • Harmony calculated from the melody instead of stored.
                • Tables that overlap their neighbours to save bytes.
                • Analog joystick input converted to digital directions, so one input routine serves both machines.

                Oddities and bugs

                A harmless pointer bug. When Bob lands safely from a jump or fall, LAND_CHECK means to write 0 (silence) to AUDC3 with the same STA (pAUDF3+1,X) that START_DEATH, a few lines earlier, uses to start its death tone. START_DEATH has X = 1 at that point, which makes the pointer pAUDC3. LAND_CHECK has X = 0, so the 6502 forms an address from bytes $59 and $5A: the high byte of the AUDF3 pointer and the low byte of the AUDC3 pointer. The result is $05D2 ($05E8 on the 5200): row $D2 of player 1, which belongs to Bob's sprite only when he is at that height, and is redrawn whenever he is (on the 5200, row $E8 is below the visible screen). Voice 3 is left as it was and is set again by the footstep code a frame later, so nobody would ever notice.

                A loop that could run forever. CLAIM_AT's search for a section's left edge scans right along a gap row until it meets girder. At a spot with no girder anywhere to the right on that row, the scan would never end. Bob's feet never stand on such a spot, so it never happens.

                Filler that does nothing. BUILD_STATION and SETUP_ITEMS contain short sequences with no effect, such as LDA #$4C / LDA $A546. $4C is the JMP opcode, so these may be places kept free for a patch. COLD_START has three NOPs, and UPDATE_ITEMS starts with a sequence that compares a ROM byte with itself minus 5 and ignores the result, padded with NOPs. That looks like a check that was patched out. The evidence for either reading is only the shape of the code.

                Tables read past their ends. The bonus for station 10 is read from one byte past the end of BONUS_BASE, which is the first byte of the next table. Station 11 reads its starting x and its transporter column from one past the end of their tables in the same way, and the jump reads two entries past the end of JUMP_ARC. The values happen to be the ones wanted.

                The poisoned goblet. Station 5's goblet kills Bob on contact. It is a deliberate test in the code, not a side effect; whether it was meant as a trap or as a protection against something is not clear.

                The credits station's mutant pointer. MUTANT_LISTS has an entry for station 11 that points into RAM ($1E18), because that word is really the first two bytes of the mutant shapes. The 88 bytes it points to are read, but through a mask of zero, so the credits get no mutants.

                The edible off-by-one. The edible time is one frame shorter than the constant suggests, because the subtraction runs with the carry clear (see "Behaviour").
